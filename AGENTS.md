# AGENTS.md

Polaris is a Symfony application. These are the rules for working in it; they win over any generic Symfony habit. The decisions behind them are in `docs/adr/`: read the relevant ADR before changing structure.

## Context

- Polaris tracks a Tesla's odometer against the lease allowance, projects mileage at lease end and warns before the limit.
- Public repo under PolyForm Noncommercial 1.0.0 (ADR 0008): the self-hostable app, personal use only. A private hosted layer builds on its Docker image and plugs in only through `src/Extension/`. Hosted-only code (billing, plans, sign-up policy, APNs keys) lives in the hosted layer.
- Stack: Symfony 8.1, PHP 8.5, PostgreSQL 18 with Doctrine ORM and Migrations, Security (form login, login throttling with Rate Limiter), Carbon, PHPUnit, Tailwind CSS 4 via symfonycasts/tailwind-bundle on AssetMapper (no npm for app assets), Stimulus, Turbo, TwigComponent, UX Icons, UX Toolkit Shadcn kit, UX Live Component ^3.6 (route `/_components`, behind the catch-all `ROLE_USER`), ApexCharts 8.3.1 (importmap, pinned; Community License does not cover embedding in a product used by others, so the hosted layer needs an OEM license; its ESM build injects its own CSS and imports `apexcharts/core`) behind one Stimulus controller. Messenger (Redis streams) and Scheduler run the fetches. Planned, not installed: Redis as the cache. `composer.json` and `symfony.lock` say what is installed.
- Work is tracked on the GitHub Project "Polaris" (https://github.com/users/RSickenberg/projects/4). Read the story's acceptance criteria and "blocked by" links; start a story once its blockers are closed.

## Workflow

- Everything runs through Docker and the Makefile (see README): `make start`, `make test` (PHPUnit in parallel through ParaTest, one database `polaris_test<token>` and one filesystem cache per worker, `PROCESSES=4` by default, `ARGS="--filter=..."`; `make test-serial` is plain PHPUnit in one process), `make ci` (php-cs-fixer, PHPStan, Deptrac, translations, PHPUnit), `make cs-fix`, `make sf ARGS="..."` for any console command. `lint:twig templates/` is not in `make ci`: run it when templates change.
- Tests read the real environment of the `php` container, and Compose loads `.env.local` into it: a local value such as `POLARIS_KEY_HOSTING=external` overrides `.env.test` (it makes `PublicKeyControllerTest` fail locally). Override it for the run: `docker compose exec -e POLARIS_KEY_HOSTING=polaris -e POLARIS_KEY_HOSTING_URL= php bin/phpunit`.
- On failure read `var/log/dev.log` and the profiler (`/_profiler`) before changing code.
- Capabilities come from `composer require <package>` and its Flex recipe. Exception: `twig-tailwind-extra` (needed by kit templates) ships a recipes-contrib recipe and `extra.symfony.allow-contrib` is `false`, so its bundle is registered by hand in `config/bundles.php`.
- With `maker-bundle`, pass every argument and `--no-interaction`; MakerBundle needs absolute class names (`make:entity '\Polaris\Lease\Entity\LeaseContract'`). If a maker still prompts, hand-write the code.
- Doctrine schema changes go through migrations (`make diff`, `make migrate`).
- The `tailwind` compose service watches and builds CSS in dev (binary and output in `var/tailwind`, volume shared with `php`); `make tailwind` builds once; `make test` and `make ci` do it first. The prod image runs `tailwind:build --minify` before `asset-map:compile`; CI builds it before PHPUnit.
- Look things up rather than from memory: `debug:router`, `debug:container`, `debug:autowiring <name>`, `debug:config <bundle>`, `config:dump-reference <bundle>`, `lint:container`, the sources in `vendor/`, and https://symfony.com/doc/current/ for the version of `composer.json`.

## Symfony conventions

Follow https://symfony.com/doc/current/best_practices.html:

- PHP attributes for framework metadata: `#[Route]`, `#[IsGranted]`, `#[Assert\...]`, `#[AsCommand]`, `#[AsEventListener]`, `#[AsMessageHandler]`, `#[AsDecorator]`, `#[AsAlias]` / `#[AsTaggedItem]` / `#[Autoconfigure]`. Routes are attributes only. A docblock sits above the attributes of its method.
- Autowiring and autoconfiguration; `#[Autowire]` (parameters, env, expressions) or `#[Target]` where a type-hint can't express it; YAML service definitions as the last resort.
- Controllers extend `AbstractController`, stay thin, delegate to services.
- Use the framework: Form, Validator, Serializer, Messenger, Security (voters, authenticators), Lock, Rate Limiter, HTTP Client, Mailer, Scheduler, Twig `path()`/`url()`. Check for a Symfony component before writing infrastructure or adding a library.
- Request data is bound by attributes: `#[MapRequestPayload]`, `#[MapQueryString]`, `#[MapQueryParameter]`.
- Constructor property promotion; `readonly` for DTOs and value objects. A service that might become `lazy: true` stays non-readonly.
- Mutual exclusion uses `symfony/lock` (`LockFactory`).

## Code

### Organization (ADR 0001)

- `src/` is organized by feature module as namespaces (no bundles): `Shared`, `Account`, `Vehicle`, `Lease`, `Reading`, `Tesla`, `Fetching`, `Alert`, `Dashboard`, `Extension`.
- Inside a module: `Entity/`, `Repository/`, `Service/`, `Message/`, `MessageHandler/`, `Controller/`, `Form/`, `Command/`, `Twig/Components/`, plus `Domain/` for calculations and value objects.
- `Domain/` is plain PHP: only its own module's `Domain/`, `Shared\Domain`, `Psr\Clock\ClockInterface`, `CarbonImmutable`; nothing from Symfony, Doctrine, HTTP, nor another module's `Domain/`. Unit-test it without the kernel.
- A module uses another only through its `Service/` classes, entities, `Domain/` types, or Messenger messages/events; never its controllers, forms, repositories or handlers. Nothing depends on `Dashboard`.
- `Service/` keeps services and interfaces at top level; value types go in subfolders by kind: `Exception/`, `Dto/` (data and result objects), `Enum/`, `Client/` (HTTP clients). They are part of the public `Api` layer.
- Templates: `templates/<module>/`; component templates: `templates/components/<Module>/`.
- Deptrac enforces this in CI (`make deptrac`). Fix the code, not the rules, unless an ADR changes them.

### Style

- Symfony coding standard (`@Symfony` php-cs-fixer ruleset, `make cs-fix`).
- Lines stay within 120 columns (php-cs-fixer does not wrap): a call or signature that does not fit puts one argument or parameter per line; a long condition or expression goes into a named variable or a small private method; a long message splits with `.` at a word.

### Data types

- DTOs (readonly classes) instead of associative arrays for app data; backed enums instead of magic strings or array keys. Arrays fine for plain lists and framework APIs.
- Entities get a ULID in the constructor (ADR 0002): `#[ORM\Id] #[ORM\Column(type: UlidType::NAME)] private Ulid $id;` with `$this->id = new Ulid();`, never `#[ORM\GeneratedValue]`. Bind ids in raw DBAL with the `ulid` type.
- A request refused by a rule throws `<Thing>Rejected` carrying a backed enum `reason` whose value is the translation key of the message (`ReadingRejected` / `ReadingRejection`, `LeaseTermsRejected`, `LeaseReturnRejected`, `ConnectionRejected`, `VehicleDataRejected`, `UserSettingsRejected`); the exception message is an English fallback, and callers branch on the reason, never on the message. Exceptions only the console shows (`TeslaSettingsRejected`, `UserCreationRejected`) carry English messages.

### Exceptions

- PHPStan checks `@throws`: a method letting `\Random\RandomException`, `\SodiumException`, `\JsonException`, Doctrine `ORMException` or `NonUniqueResultException`, or a `symfony/lock` exception through must list it (`exceptions.checkedExceptionClasses` in `phpstan.dist.neon`). Controllers, commands and tests are exempt. A caller of a documented method documents it too unless it catches it.

### Assertions

- `\assert()` only narrows a type or states an invariant that cannot fail (e.g. after a Carbon call PHPStan types as `static|string`). Never use it to validate input, guard a possible state, or for side effects: production runs `zend.assertions = -1` (`frankenphp/conf.d/20-app.prod.ini`); dev and tests keep it on.

### Dates, units and business rules

- UTC everywhere (ADR 0003): storage, computation, API, logs; the kernel forces UTC. Current time from `ClockInterface`, never `new \DateTimeImmutable()` or `time()`. `CarbonImmutable`, never `Carbon`. The user's time zone is only for display and converting fetch slots.
- Distances are stored as integer metres. The Tesla odometer is in miles: 1 mi = 1.609344 km.
- The lease allowance is linear over the whole term: total km = km per year x years, no yearly reset.

### Tests

- Functional tests extend `WebTestCase`, service tests `KernelTestCase`, `Domain/` tests plain `TestCase`. A feature is done with a test that exercises it as a caller would (HTTP request for a controller, service call for a service).
- Functional tests sign in with `Polaris\Tests\Support\SignsIn`; post the login form only when testing login.
- A test of a self-hosted default of `src/Extension/`, or one whose expectations follow from it, sets that default in the container itself before the first service that reads it (`self::getContainer()->set(ErrorReportingPolicy::class, new SelfHostedErrorReportingPolicy())`). The hosted layer replaces these defaults and its CI runs this suite: a test that takes the default from the container fails there.
- Tests never reach the network: `MockHttpClient`, swapped in with `getContainer()->set('http_client', $client)` (public alias `test.polaris.http_client` in `when@test`).
- Hand-worked figures are explained in a comment beside the case, and expected values that are not obvious are named (named arguments or keys rather than positional tuples).

## UI

- Pages extend `base.html.twig`, fill `main`, and start with `<twig:Shared:PageHeader title="..." subject="{{ vehicle.name }}">` (the h1, the vehicle in a lighter tone, the page actions as its content). A section of a page is a kit `Card` whose `Card:Title` holds an `h2`. Tables: `Table` inside `Card`.
- Kit components: `bin/console ux:install <name> --kit shadcn` into `templates/components/` (controllers into `assets/controllers/`); ours to edit but keep edits minimal so a later `ux:install` diff stays readable (so far translation keys replace hardcoded English, and `Alert:Description` is `text-pretty` instead of `text-balance` on a phone, which broke lines early). `symfony/ux-toolkit` is a dev dependency; installed files are committed.
- Polaris components: `templates/components/<Module>/`. `Shared`: the shell (`AppSidebar`, `PageHeader`, `LocaleSwitcher`, `ThemeToggle`, toasts). `Dashboard`, anonymous, built on kit Card, Progress, Badge, Alert, Dialog: `KpiCard` (`value` already formatted, `unit`, `hint`), `PaceCard`, `LeaseProgress`, `RiskAlert`, `MileageChart`, `ComparisonPanel`, `CardHelp` (the info button and dialog of a card). `Tesla:TokenStorageCard`.
- Colours: `app.css` holds the theme tokens. The tones `success`, `warning`, `info`, `danger` each have a stroke, a `-surface` and a `-foreground` (Tailwind `bg-success-surface`, `text-warning-foreground`, `border-info`); `--risk-ok`, `--risk-watch`, `--risk-over` take them, and `--risk-*-projection` is the lighter shade of the projected curve. Strokes keep 3:1 against the background (WCAG 1.4.11), and a risk level always comes with its icon and its words, never colour alone.
- Figures: every figure on a page goes through the filters of `Shared\Twig\FigureExtension`: `figure(maxDecimals)`, `km(maxDecimals)` for a `Distance`, `money` for a `Money`, `amount(currency)`, `percent`. They follow `Shared\Domain\NumberConvention`: French is written the Swiss way (fr_CH formats, so a point in amounts and `45%`, and an apostrophe between thousands: 12’345); other languages keep ICU's defaults. `Shared\Service\FigureMessageFormatter` (decorating `translator.formatter`) applies the same convention to `{x, number}` in ICU messages, and `chart_controller.js` gets it as its `locale` and `grouping` values. The dashboard figures use a light weight, not monospace; only the comparison panels monospace their digits. The figures of the risk message are bold.
- The dashboard order: the risk alert, the main figures (projected at lease end, driven, allowed to date, last reading), the progress bar, the chart, the pace cards, the comparison panels. `Dashboard\Service\DashboardService` decides what the template shows: `DashboardState` (`canRefresh()`, `hasEnded()`), `RiskMessage` (the sentence under the risk level; every message takes the same parameters, figures formatted, escaped and wrapped in `<strong>` by the template, which prints the message raw). Templates compare enums (`enum('...DashboardState').Active`), never their string values.
- `Fetching:OdometerRefreshButton` (`Fetching\Twig\Components\OdometerRefreshButton`, template `templates/components/Fetching/`) is the first PHP-backed Live Component; `config/packages/twig_component.yaml` maps `Polaris\Fetching\Twig\Components\` to name prefix `Fetching`. It sits in the page header of the dashboard while the lease runs. Live Component 3.6 guards actions only by POST plus `X-Requested-With` (no CSRF token) and has no `#[IsGranted]`: the component checks `VehiclePermission::Manage` itself on every request (render and action) and answers 404. A `LiveProp` named like a component method breaks hydration. When a refresh ends `Stored` or `Unchanged` (`RefreshOutcome::movesFigures()`) it renders a hidden `data-controller="dashboard-refresh"` element (id per click), which asks Turbo for a page refresh: the dashboard sets the `turbo-refresh-method` meta to `morph` (and keeps the scroll), and `chart_controller.js` updates its chart in place when its `series` or `options` values change. The morph after a refresh is unverified in a real browser.
- `assets/controllers/chart_controller.js` is the one generic chart controller: type, series, options, `locale`, `grouping`, `timeZone` are Stimulus values; option strings `var(--token)` resolve from theme tokens; it redraws when `<html>` `dark` changes, formats with Intl, and destroys the chart on disconnect and before the Turbo cache. `Dashboard\Domain\MileageSeriesBuilder` builds the curves (readonly DTOs, no Lease domain types) from the dashboard's assessment; driven and projected curves take the risk colour of the alert. Zoom presets (7 days, 30 days, 1 year, to lease end, whole lease) are `Dashboard\Domain\MileageRangeBuilder`: look-back windows end now and start no earlier than the lease start; the forecast window exists only with a projection; buttons drive the controller's `zoom` action. A zoom also fits the y axis to the values inside the window (8% of air, never under 0); a window that runs to the end of the data (whole lease, to lease end) keeps the axis the options give.
- Flash messages and notices are toasts. Controllers add flashes with a `Shared\Service\Enum\ToastVariant` (`addFlash(ToastVariant::Success->value, ...)`: `success`, `info`, `warning`, `danger`; Symfony's `error` type is shown as `danger`). `base.html.twig` renders `<twig:Shared:ToastRegion />` once (the fixed top-right `toast-region`, `aria-live`; login renders it itself). It renders the session flashes as `Shared:Toast` (kit Alert, `data-flash`; danger stays until dismissed, others leave after 6 s, paused on hover or focus) and hands one empty toast per variant to `toast_region_controller.js`, which shows any `polaris:toast` window event (`detail: {variant, message}`). A Live Component announces a toast with `<twig:Shared:ToastAnnounce :id :variant :message>`, a hidden element whose `id` changes per message (a morphed element that keeps its `id` says nothing twice). Inside a `<twig:...>` tag the variable `variant` is the child's: set anything derived from your own beforehand.
- Dates: `localized_datetime(timeZone)` writes an instant in the user's zone with its offset (it tells apart the two 02:30 of a daylight saving change); the last reading uses `humanized_datetime` ("Today at ...", "Yesterday at ...", older in full), days in the user's time zone, "now" from the clock.
- Icons are Lucide: `bin/console ux:icons:import lucide:<name>` into `assets/icons/`, committed (no runtime Iconify call). The favicon is `assets/images/favicon.svg`, the gauge of Lucide.
- Dark mode is the `dark` class on `<html>`, set before first paint by the inline script of `base.html.twig`, kept by `theme_controller.js`.
- `app.css` styles no bare element: titles, paragraphs and lists carry utility classes.
- Forms use the global theme `templates/shared/form_theme.html.twig` (in `twig.form_themes`), extending `form_div_layout.html.twig` and overriding only needed blocks: rows are kit `Field` (`Field:Label`, control, `Field:Description` for `help`, one `Field:Error` per error); text-like widgets `Input`; choice selects `NativeSelect` (size `sm`); buttons `Button`; checkboxes (alone or expanded choice, one line per choice, no asterisk) kit `Checkbox`. A newline in a help text (`help` translation) becomes a line break (`nl2br`). `form_row` already passes `aria-describedby`/`aria-invalid` via `attr`; the theme forwards them. The file widget is a kit `Input` (its button is visible); a submit button can carry a Lucide icon before its label with `attr: {'data-icon': 'lucide:upload'}`. Radio, range, color widgets are not themed (default layout).

## Translations

- Locales `en` (default, fallback) and `fr` in `config/packages/translation.yaml`. `Shared\EventListener\LocaleListener` picks the request locale through the framework-free `Shared\Domain\LocaleNegotiator`: user preference (`Shared\Service\PreferredLocaleProvider`), then best `Accept-Language` match, then `en`.
- Switcher `Shared\Controller\LocaleController` (`/locale/{locale}`) stores the `polaris_locale` cookie (`CookiePreferredLocaleProvider`) and dispatches `Shared\Event\LocaleSwitched`. `Account\Service\UserPreferredLocaleProvider` decorates the cookie provider and reads the user's locale from the session, where `RememberLocaleOnLogin` and `SaveSwitchedLocale` put it (the latter also writes `User.locale`). It can't read the token: `LocaleListener` runs at priority 20, before the firewall (8). A new language also needs its `locale.<code>` key in `shared`.
- Never write user-facing text in a template, form, flash, validator or email: use a key. Exceptions: console commands (English), brand names (`Polaris`).
- One XLIFF 1.2 domain per module: `translations/<domain>.<locale>.xlf`, `<domain>` = lowercase module name, plus `shared` for multi-module text. Source = key, target = text, `id` repeats the key. Constraint and callback messages live in `validators` with keys starting with the module (`reading.odometer.too_large`).
- Keys: lowercase `snake_case` segments joined by `.`, max three levels, no module prefix: `page.history.title`, `form.odometer.label`, `form.submit`, `flash.reading_added`, `rejected.in_future`, `table.empty`. Form labels/buttons: `form.<field>.label`, `form.submit`. Pass the domain explicitly: `|trans(domain='reading')`, `$translator->trans($key, $params, 'reading')`, or `translation_domain` on the form type.
- A message formatting a number or date goes in `<domain>+intl-icu.<locale>.xlf` (ICU: `{limit, number}`, `{at, date, medium}`); code passes raw numbers/timestamps. No apostrophes in these files (ICU escape; use `’`). Other messages use `%name%`.
- Format numbers and dates in Twig for the active locale (`format_number`, `format_currency`, `localized_datetime(timeZone)`), never `number_format()` or fixed patterns. Stored and computed in UTC; the time zone only converts for display.
- Add a key: `en` and `fr` file of its domain in the same change. Add a language: copy every `*.en.xlf` to `*.<locale>.xlf`, translate targets, add the locale to `enabled_locales` and the `fr` checks, extend tests.
- CI runs `composer translations` (`make translations`): `lint:xliff translations`, `lint:translations`, `debug:translation fr --only-missing` (a key used in code but absent from `fr` fails). It can't see run-time keys (enum values like `source.manual`), so `TranslationFilesTest` compares every `en` file with its `fr` twin key by key and placeholder by placeholder.

## Modules

### Account: accounts and access

- Single user when self-hosted. `Account\Entity\User` (table `app_user`) holds email (unique, trimmed, lower-cased), password hash (property `password`), `locale`, `timeZone` (IANA, `UTC` default). Created only by `Account\Service\UserCreator` (console `polaris:user:create`), gated by `Extension\SignUpPolicy` (default `SingleUserSignUpPolicy` allows one user; the hosted layer replaces it). The command reads the password from a hidden prompt or stdin, never an argument/option, and never prints it.
- Access is denied by default: `access_control` in `config/packages/security.yaml` ends with `^/` requiring `ROLE_USER`; public exceptions (`/login`, `/locale/`) sit above. A new public page needs an entry there and in `PUBLIC_ROUTES` of `AccessControlTest`, which walks the router and fails on any anonymously reachable route. Login: `Account\Controller\LoginController` (`account_login`, `templates/account/login.html.twig`, bare layout via the `body` block of `base.html.twig`); logout is in the sidebar footer.
- Settings (`Account\Controller\SettingsController`, `/settings`): forms `profile` (email, locale, time zone) and `password` (current, new twice) via `Account\Service\UserSettings`. A changed email or password stales the session, so the controller re-signs in with `Security::login()`. When API tokens exist (ADR 0005), `changePassword()` must revoke them. Sidebar menu: `templates/components/Shared/AppSidebar.html.twig` (the account menu marks the page the user is on with `aria-current=page`, and opens focused on it; the settings pages have no `max-w-*`, they use the width of the dashboard); avatar letters: `Account\Domain\Initials`.
- Password reset (`PasswordResetController`, `PasswordResetService`): `PasswordResetRequest` stores a selector and the sha256 of a verifier (`Account\Domain\ResetToken`), never the link. Asking never reveals whether the email exists, is limited by the `password_reset` limiter (per client address), and sends at most one link per 2 minutes per account. Link built from `DEFAULT_URI`, not the request host. `changePassword()` removes pending requests. Emails use the user's language (`account` domain); the mailer needs `MAILER_DSN`, `MAILER_FROM`, `DEFAULT_URI`.
- Form login and logout use stateless CSRF ids `authenticate` and `logout`; `login_throttling` allows 5 attempts per 15 minutes. The `dev` firewall (profiler, toolbar, AssetMapper open) is driven by `polaris.security.open_paths`, which matches nothing in production.
- Pages showing or taking dates read the time zone from the user (`#[CurrentUser] User $user`). `Vehicle::$owner` (required) links every vehicle to its user; users reach only their own: every action taking a vehicle carries `#[IsGranted(VehiclePermission::Manage->value, 'vehicle', statusCode: Response::HTTP_NOT_FOUND)]` (`Vehicle\Security\VehicleVoter`), and vehicle-listing queries filter on `owner`. A new vehicle page needs the attribute and a test in `VehicleOwnershipTest`.

### Account and Shared: the owner's midnight (#107)

- Every daily job runs at the owner's local midnight (`User::$timeZone`), never at a UTC time. `Shared\Domain\OwnerMidnight` (plain PHP, unit tested) is the one place it is computed: `at` is the first instant of the local calendar day (where midnight does not exist that day, the first instant that does), `localDay` is the date it opens as midnight UTC (a label, not an instant). `latestDue()` takes the latest midnight whose jobs are due, 5 minutes after it (a reading stamped just before it can still be queued); `latestAt()` the latest midnight at or before now; `opening()` and `of()` rebuild one.
- `Account\Service\OwnerMidnightDispatcher`, run by the `DispatchOwnerMidnights` tick, queues one `Account\Message\OwnerMidnightPassed` (user id, local day, midnight instant) on `async` per owner and local day. The marker is `User::$lastMidnightDay`, moved by one compare-and-set UPDATE (`UserRepository::claimMidnight()`) before the message is queued: of two ticks or two workers exactly one wins, so a doubled tick or a restart runs nothing twice; if queuing fails the claim is given back. After an outage only the latest missed midnight runs (no catch-up per missed day). A changed time zone never runs a label twice; a jump forward can skip a label. A new user runs their latest midnight on the first tick.
- Each module with daily work handles `OwnerMidnightPassed`: Lease queues one `SaveProjectionSnapshot` per lease of the owner (`QueueOwnerProjectionSnapshotsHandler`), Fetching purges the owner's attempts (`PurgeOwnerRefreshAttemptsHandler`). A new daily job is a handler of this message, never a cron entry. `OwnerMidnightPassed` implements `Shared\Reporting\ReportsForUser`, which `BindReportingUserOfMessage` turns into the reporting user.
- Not on the owner's midnight, on purpose: lease start and end dates (`LeaseTerm`, calendar dates at midnight UTC), the wake cap, the manual refresh limiter, `FetchSlotRun` and `RefreshAttempt` retention (rolling windows).

### Tesla: Fleet API rules

- The car is woken only on a manual refresh the user confirmed, within the daily wake cap (see "Waking the car"); everything else reads a car that is already online.
- Scheduled reads run only when the state is `online`. Manual refresh: once per hour per vehicle.
- Minimal OAuth scopes. Tokens encrypted at rest; refresh tokens single-use, rotated under a lock.
- Tesla can revoke API access at any time: manual odometer entry must always keep working.

### Tesla: key pair

- `Tesla\Entity\TeslaApp` (owned by a `User`) holds the prime256v1 public key in clear (PKIX PEM) and the private key as `Shared\Service\SecretEncrypter` ciphertext (ADR 0007: libsodium secretbox, `v1:` prefix, key `POLARIS_ENCRYPTION_KEY`). Private PEM is PKCS8; vehicle-command reads PKCS8 and SEC1 (checked in source, not run). Never log, dump or echo it: `Tesla\Domain\KeyPair` and `TeslaApp::__serialize()` leave it out.
- `polaris:tesla:keygen` (`TeslaKeyService`) refuses to replace a key without `--force`.
- `Extension\PublicKeyHosting` decides where Tesla finds the public key. Default `ConfiguredPublicKeyHosting` follows `POLARIS_KEY_HOSTING`: `polaris` (`PolarisPublicKeyHosting`; `Tesla\Controller\PublicKeyController` serves the only app's key whatever the Host, stateless, public) or `external` (`ExternalPublicKeyHosting` writes the PEM into `POLARIS_KEY_HOSTING_DIR` when set; `POLARIS_KEY_HOSTING_URL`, the https URL of the PEM, makes `publicKeyUrl()` non-null so `PublicKeyChecker` reads that URL; either is enough; the route then 404s). The hosted layer replaces the alias and implements `publicKeyUrl()` (null keeps the app domain).
- The well-known route is public: its `access_control` entry precedes the catch-all and `tesla_public_key` is in `PUBLIC_ROUTES`.

### Tesla: app credentials and registration

- `TeslaApp` also holds `clientId`, `encryptedClientSecret` (SecretEncrypter, out of `__serialize`), `domain` (host serving the public key, `Tesla\Domain\AppDomain`; not derived from `DEFAULT_URI`) and `enabledRegions` (`Tesla\Domain\FleetRegion`). Keygen creates the row, so `TeslaAppSettings::save()` and `polaris:tesla:configure` need the key pair first. `TeslaOwnerFinder` resolves the user for every Tesla command.
- `FleetRegion`: `na`, `eu`, `cn`. China is a separate Tesla account/developer app: the case exists only to be refused (`isSupported()` false, `tokenUrl()` throws, settings and `register` reject it). The NA and EMEA token host is `fleet-auth.prd.vn.cloud.tesla.com`.

- Unverified (undocumented): the register body (`{"domain": ...}`); Tesla error body shape (`FleetApiError` reads `error`, `error_description`, `error_message`, `message`, else truncated body); public key response (`response.public_key`, PEM or hex of the uncompressed point, see `PublicKeyFormat`). The first real run confirmed the partner token needs a scope (`openid vehicle_device_data`; without one the key read-back gave 403 "missing scopes") and that register works for `eu`.
- Settings page "Tesla settings" (`Tesla\Controller\TeslaSettingsController`, `/settings/tesla`, linked from the account menu; never call it "Tesla app", which users read as Tesla's phone app) edits the same settings via `TeslaAppSettings` and `Tesla\Form\Model\TeslaAppSettingsFormData`. App found by owner (no id in URL); client secret field write-only (never rendered, empty keeps stored); China listed but disabled and rejected server-side; without a key pair it shows how to run keygen; it doesn't register (`key:check`, `register` stay on the console). It (last card) and the consent page (below the consent form, where the user agrees that tokens are stored) show `Tesla:TokenStorageCard` (templates/components/Tesla/): how tokens are stored, each paragraph with a Lucide glyph, and links to the code on GitHub built from the `polaris.source_url` parameter (Twig global `polaris_source_url`; a fork changes the parameter). Keep the card true when the storage changes, and keep the literal `v1:` out of it (a test asserts no ciphertext prefix reaches the page). Pass the app to the template as `teslaApp` (`app` is the Twig global).

### Tesla: connection and tokens

- `Tesla\Entity\OAuthToken` (one per `TeslaApp`): access and refresh tokens as SecretEncrypter ciphertext (out of `__serialize`), `expiresAt` (UTC), scopes, `ConnectionStatus` (`Connected`, `Expired`), `ConnectionMethod`, the user's Fleet API base URL. `TeslaApp::$consentGivenAt` records the opt-in consent (Fleet API Agreement 9.3.7); every way to connect is refused without it (`ConnectionRejected::NO_CONSENT`) and pages redirect to `/settings/tesla/consent`.
- `Tesla\Service\OAuthClient`: authorize URL, code exchange (needs `audience` and client secret), refresh (only `client_id` and `refresh_token`), `GET /api/1/users/region`. No PKCE (undocumented by Tesla). Shares `SendsFleetApiRequests` (secret redaction, no redirects) with `FleetApiClient`. No call is retried: a refresh token is single use.
- `TeslaConnectionService` is the only way to connect (redirect callback, pasted callback URL, pasted refresh token) and disconnect. `state` is kept in the session by `TeslaConnectionController` and checked in the service. Redirect URI from `RedirectUriProvider` (`POLARIS_TESLA_REDIRECT_URI`, else `DEFAULT_URI` + `/tesla/callback`), sent unchanged to `/authorize` and `/token`.
- Anything needing an access token calls `TokenProvider::accessToken()` (`LockedTokenProvider`): refreshes `POLARIS_TESLA_REFRESH_MARGIN` seconds before expiry under a `symfony/lock` lock per app (`LOCK_DSN`, Redis in Compose), re-reads the row once locked, commits the new refresh token in a transaction before returning. A refused refresh token (`login_required`, `invalid_grant`, any 401) marks the row `Expired` and throws `TeslaNotConnected`; an outage leaves the row alone. `polaris:tesla:token:refresh [--force]` runs it by hand (prints only the new expiry).
- Unverified: the `users/region` answer shape (`response.region`, `response.fleet_api_base_url`); behaviour when account region differs from audience; whether `http://localhost:8000/tesla/callback` completes the flow.
- A refused connection is `ConnectionRejected` with a `ConnectionRejection` reason (the translation key in `tesla`). The callback binds `code`, `state` and `error` with `#[MapQueryParameter]`; an empty value counts as missing.

### Tesla: vehicle reads

- `Tesla\Service\VehicleClient` (impl. `Client\TeslaFleetClient`, read-only) lists vehicles (`GET /api/1/vehicles`, first page only), reads a state (`/vehicles/{vin}`, `VehicleState`) and a live odometer (`/vehicles/{vin}/vehicle_data`, `OdometerReading`). Callers pass `TeslaApp` and `Vin`; the client gets the token from `TokenProvider` and the base URL from the stored `OAuthToken`, lets `TeslaNotConnected` through (before any HTTP call), has no wake method (the wake is `VehicleCommandClient`, see "Waking the car"), and sends no `endpoints` query (never `location_data`). Odometer = `Distance::fromMiles()` of `vehicle_state.odometer`; a missing/invalid one or an unknown state value is `FleetApiError::unexpected`.
- `TeslaOdometerReader::read()`: state first, then `vehicle_data` only when `online`. `asleep`/`offline` give `NoReadingReason::Asleep|Offline` without asking the car; a 408 on the live call gives `Unavailable`, not retried. The user wakes the car in the Tesla app and refetches, or confirms a wake from Polaris (see "Waking the car"). The reader itself never wakes the car. An opt-in daily automatic wake stays out of scope: it needs an ADR and a change of the rule below.
- `vehicle_data_cached` is unused: a real offline answer has no `odometer` in `vehicle_state`. Its `timestamp` blocks are epoch milliseconds.
- Retries only on this client (`RetryableHttpClient` built in its constructor): 500, 502, 503, 504, 540; max 2 retries; delay `polaris.tesla.retry_delay_ms` (500 ms, doubling, cap 4 s, `0` in tests); `Retry-After` honoured. Never retry 408 (car not online; every status below 500 is billed), 401, 403, 404, 412, 421, 429. `OAuthClient` and `FleetApiClient` keep the plain `http_client` (single-use refresh token must never be sent twice). Don't configure `retry_failed` globally.
- The fetch job compares a reading with the last stored one and saves it; this module only reads.
- `polaris:tesla:debug:fetch list|state|data|cached [vin] [--redact]` prints the raw answer, whole by default; `--redact` removes VIN, ids, car names, tokens, location, `drive_state` (for issues/fixtures). `data` is a billed live call. GET only, never `wake_up`.
- Confirmed by real EU answers: vehicle list and vehicle shape (`state` `online`, `offline`), live `vehicle_data` (`response.vehicle_state.odometer` float, `vehicle_state.timestamp` epoch ms, used as read time, clock only if missing), 408 body (`error: "vehicle unavailable: vehicle is offline or asleep"`).
- Every live `vehicle_data` answer is kept for later use, only if the user allowed it (`TeslaApp::$keepVehicleData`, a checkbox on `/settings/tesla`, on by default; turning it off stops new copies and deletes none; `TeslaAppSettingsData` fields `dailyWakeCap` and `keepVehicleData` are nullable, null keeps the stored value, so `polaris:tesla:configure` never resets them): `OdometerReading::$payload` carries the `response` object, `Tesla\Domain\VehicleDataRedactor` strips the location keys (`latitude`, `longitude`, `heading`, `native_*`, `gps_as_of`, `location_data`; the answer can carry them in `drive_state` even though we never ask), and `OdometerFetcher` hands it to `Reading\Service\VehicleDataRecorder` before the odometer is compared. Table `vehicle_data_snapshot` (`Reading\Entity\VehicleDataSnapshot`: vehicle, `captured_at` = Tesla's timestamp, `received_at`, JSONB `payload`), unique per (vehicle, `captured_at`), so a value that did not change still gets a row and the same instant is stored once. Never stored: the location, tokens, anything from a car that was not read. No retention yet (about 5 to 10 KB per read). JSONB does not tell `100` from `100.0`.
- The API odometer is always miles, whatever `gui_settings.gui_distance_units` says; no unit field.
- Unverified: `/vehicles` paging parameters (only the answer's `pagination` object seen); the `endpoints` parameter; the `asleep` state value; that a 408 means a car that fell asleep after an `online` state.

### Vehicle: vehicles, save and import

- Created by `Vehicle\Service\TeslaVehicleImporter` (Tesla account list via `VehicleClient::listVehicles()`, first page only; no car contacted), `polaris:vehicle:import [--vin=] [--dry-run]`, page `/vehicles/import` (`VehicleImportController`, route priority above `/vehicles/{id}`, domain `vehicle`), or `polaris:vehicle:add <vin> <name>`. The importer re-reads the listing: a posted VIN is only a choice among returned vehicles. VIN is unique across users (existing = "already added"). Name: Tesla display name, else `Tesla` + last 4 VIN characters. The home page links to the import page.

- A self-hosted Polaris has one vehicle per user. `Extension\VehicleLimitPolicy::limit(User)` (int, null = no limit; default `SingleVehicleLimitPolicy` returns 1, the hosted layer replaces it) is applied by `Vehicle\Service\VehicleQuota` (`remaining()`, `assertCanAdd()` throws `VehicleLimitReached`) before a vehicle is created: `TeslaVehicleImporter::import()` (the whole request is refused when the vehicles to add are more than the owner may still have, nothing is added), `polaris:vehicle:add`, and the import page (an owner at the limit gets the `limit_reached` state without any call to Tesla; too many ticked boxes give a danger toast and the form again). Vehicles already there are never removed, and the dev seed and the data import (which fill an existing vehicle) are not limited. A test needing several vehicles for one user uses `Tests\Support\LiftsVehicleLimit` (call it right after booting the kernel, before the first service that reads the policy).

- Save and import (Vehicle module): page `/vehicles/{id}/data` (`VehicleDataController`, route `vehicle_data`, sidebar item "Data"; download `vehicle_data_export`, an upload form `VehicleDataImportType`, 10 MB at most) and the console `polaris:vehicle:data:export <vin> [--file=]` / `polaris:vehicle:data:import <vin> <file>` (not `polaris:vehicle:import`, which imports from the Tesla account). `Vehicle\Service\VehicleDataExporter` writes one JSON file (`format` `polaris.vehicle-data`, `version` 1): the lease (with `returnedAt`), the readings oldest first (source, raw Tesla odometer and unit, `lastVerifiedAt`) and the projection snapshots; never the VIN, the Tesla tokens or the raw `vehicle_data` answers (they can carry a location). Distances are integer metres, instants ISO 8601 UTC, local days `Y-m-d`. `VehicleDataImporter` reads and checks the whole file first (`Vehicle\Domain\JsonObject` names the path of a wrong value; `VehicleDataRejected` with a `VehicleDataRejection` reason (a `data.rejected.*` key: not JSON, not an export, unknown version, invalid value) and an English `detail`; odometer going down is invalid), then writes in one transaction. It only adds, so importing a file twice changes nothing: the lease (`LeaseTermsService::import()`) is created only when the vehicle has none, readings (`OdometerReadingService::import()`) are skipped at an instant already stored and refused when in the future or against the order of the stored readings, snapshots (`ProjectionSnapshotService::import()`, still the only writer) are skipped for a local day that has one or when they lack the cutoff or the pace (rows saved before #107), or when there is no lease. The vehicle is chosen by the user, the file does not say which car it is. A new version of the format needs a reader of the old one.

### Fetching: scheduled fetching and manual refresh

- Messenger (`config/packages/messenger.yaml`): three Redis stream transports on `MESSENGER_TRANSPORT_DSN`: `async` (nothing routed), `tesla` (`FetchOdometerMessage`, no Messenger retry: a billed read repeats only via the hourly rule) and `failed` (`failure_transport`, retried by hand with `messenger:failed:retry`). The `worker` service (`frankenphp/docker-worker.sh`) consumes `scheduler_default async tesla` explicitly, never `--all` (it would drain `failed` in a loop). Tests use `in-memory://` transports (`messenger.transport.tesla`).
- `Scheduler\FetchScheduleProvider` has two recurring messages in one `with()` call, both the every-minute cron (UTC cron, `every('5 minutes')` counts from worker start): `DispatchDueFetches` and `Account\Message\DispatchOwnerMidnights`. Stateful, not locked (a lock held by a killed worker would silence ticks after restart; `FetchSlotRun` uniqueness and the owner claim below already prevent double queuing). No daily entry and no UTC time of day: a daily job runs at the owner's local midnight (see "Owner's midnight"). Slots aren't cron entries: `Service\DueFetchDispatcher` converts each vehicle's local slots to UTC with `Domain\SlotCalculator` every tick (owner's time zone, so DST needs no restart) and queues a `FetchOdometerMessage` for each slot whose window is open (`Domain\FetchWindow`: slot to +3 h) and has no `FetchSlotRun`. The row is written first and unique on (vehicle, slot); a window closed while the worker was down is not run late.
- A returned lease (see "Returned lease") is not fetched: `DueFetchDispatcher` skips the vehicle (`LeaseReturnService::isReturned()`) (no `FetchSlotRun`, no message); `OdometerFetcher` re-checks under the vehicle lock, before any Tesla call (not even the state), and ends a queued scheduled message `SlotRunStatus::Skipped` and a manual one `RefreshOutcome::Returned`. `ManualRefreshService::request()` answers `RefreshRequestStatus::Returned` (a later API: 409) and `wakeOffer()` / `requestWake()` `WakeRequestStatus::Returned`; the refresh button is not on a returned dashboard. After an undo fetching resumes at the next slot whose window is open, with no catch-up of closed ones.
- Slots: `FetchSchedule` (one per vehicle, 1 or 2 `HH:MM` local times; none stored = 21:00), set by `polaris:fetch:schedule [--vin=] [first [second]]` via `Service\FetchScheduleService`.
- `Service\OdometerFetcher` runs the message (its docblock defines the words: a check is one look at the car for a slot, `FetchOdometerMessage::$attempt` is the index of the check, a refresh is a `RefreshAttempt`) with `TeslaOdometerReader` (never wakes the car unless the message says `allowWake` and has a refresh id, see "Waking the car"). Not online: re-queues with `attempt + 1` and a `DelayStamp` to the next hour after the slot (`FetchWindow::retryDelaySeconds()`, so a late first check doesn't shift the rest), max 4 state checks (`FetchWindow::MAX_ATTEMPTS`), then `Skipped`. `OdometerReadingService::recordFromApi()` stores a value only if it differs from the previous (`readAt` = Tesla's `vehicle_state.timestamp`); lower than a stored reading = `Rejected`, warning, never retried. `TeslaNotConnected` ends the slot `NotConnected` with a warning; other `FleetApiError`s are rethrown to `failed`. After a read that Tesla answered, `SlotRunLedger::purgeOld()` deletes the vehicle's `FetchSlotRun`s older than 24 h (their 3 h window is long closed), after the flush of the run, so nothing is written to a deleted row; a vehicle that never gets an answer keeps them.
- `FetchOdometerMessage` has scalar fields; null `slotTimestamp` = a fetch with no slot (manual refresh, never retried). New fields go at the end with a default; `wakeDeadline` is the latest (after `refreshId` and `allowWake`).
- `OdometerFetcher` runs one fetch per vehicle at a time, scheduled or manual, under a `symfony/lock` lock `odometer_fetch_<vehicle base32>` (TTL 60 s, non-blocking). Held: a manual refresh ends `RefreshOutcome::Busy` and asks nothing; a scheduled check is re-queued 30 s later with the same `attempt`.
- Manual refresh: `Service\ManualRefreshService::request()` is the only entry (component and a later `POST /api/vehicles/{id}/refresh` use it and read `RefreshRequestResult`: `Accepted` = 202, `RateLimited` with `retryAfter` = 429). The limit is decided there, not in the UI, but spent by the fetch: `Service\ManualRefreshLimit` (policy plus limiter) is only looked at (`retryAfter()`, `reserve(0)`) by `request()` and `requestWake()`, and consumed by `OdometerFetcher` right before the billed live read of an online car, after the free state check. A car found asleep, offline or not read costs nothing against the hour; a read that finds the hour spent meanwhile ends `RefreshOutcome::Limited`; a wake is refused (`WakeRequestStatus::RateLimited`, `RefreshOutcome::Limited` in the fetch) while the hour is spent, since no read could follow it. Scheduled reads neither consume nor are held by it. `Extension\ManualRefreshPolicy` says whether a vehicle is limited (self-hosted default `ConfiguredManualRefreshPolicy`, `POLARIS_MANUAL_REFRESH_LIMIT`: `1` limits, `0` lifts it; the hosted layer replaces it and always limits). The `manual_refresh` limiter (`fixed_window`, 1/hour, key = vehicle id, default `cache.rate_limiter` pool = filesystem app cache: one web container only, move to Redis with the cache) counts one billed read per vehicle and hour. The Symfony limiter reads the wall clock, so tests age its stored `Window` rather than freeze time. An accepted request writes a `RefreshAttempt` (`Queued`) and dispatches `FetchOdometerMessage` with null slot and `refreshId`; the fetcher settles it (`RefreshOutcome`: `Stored`, `Unchanged`, `Asleep`, `Offline`, `Unavailable`, `NotConnected`, `Rejected`, `Busy`, `Limited`, `Failed`); the component polls every 2 s (`data-poll`) for at most 2 minutes and builds its toast in PHP (`toast(): ?RefreshToast`, variant from the outcome). `RefreshAttempt`s are deleted after 24 h by `Service\RefreshAttemptPurger::purgeOf()`, per owner at the owner's midnight (`PurgeOwnerRefreshAttemptsHandler` on `OwnerMidnightPassed`); the retention is still a rolling 24 h and an attempt stays while its `wokeAt` is younger too, since the wake cap counts wakes from these rows. A car found asleep is woken only after the user confirmed it (see "Waking the car").

### Fetching and Tesla: waking the car (#32)

- Only a manual refresh the user confirmed wakes a car (the rule itself: "Fleet API rules" in the Tesla section). The refresh settles `Asleep`; the component then asks `ManualRefreshService::wakeOffer()` and, for `WakeRequestStatus::Accepted`, opens the kit Dialog (cost per wake from `polaris.tesla.wake_cost` and `polaris.tesla.wake_currency`, formatted in Twig; asked every time, no remembered choice) with "Use last reading" and "Wake and refresh". `requestWake()` continues the same `RefreshAttempt` (back to `Queued`, `allowWake: true`): it spends the daily wake cap, not a second hourly refresh. Confirmable for 10 minutes after the refresh (`WakeWindow::CONFIRM_SECONDS`). The typed result `WakeRequestResult` / `WakeRequestStatus` (`Accepted` = 202, `CapReached` with `availableAt` = 429, `ScopeMissing`, `NotConnected`, `NothingToWake`) is what a later `POST /api/vehicles/{id}/refresh` with `{"wake": true}` reuses.
- A scheduled fetch never wakes: `OdometerFetcher` wakes only when `allowWake` is set, the message has no slot and carries the refresh id, and the state read says `asleep` or `offline`. The one exception is opt-in: with `TeslaApp::$wakeOnLastCheck` (checkbox on `/settings/tesla`, off by default), the last state check of a slot window (`FetchWindow::isLastAttempt()`, about 3 h after the slot) that finds the car asleep or offline wakes it, on the same rules (scope, daily cap, poll); a `RefreshAttempt` is created for it (the cap counts those), the message keeps its slot, and the slot run stays `Retrying` until the poll reads the car (`Stored`/`Unchanged`) or gives up (`Skipped`). The hourly manual limit neither holds nor is spent by it. Whether Tesla can wake an `offline` car is not documented (the best practices page only says to check it is neither): the offer is made anyway, with a dialog that promises nothing (`wake.dialog_offline`), and `RefreshAttempt::$wokeFrom` (`NoReadingReason`) keeps what the check said before the wake. With `outcome` (`Stored`/`Unchanged` = it came online, `WakeTimeout` = it did not) a query on `refresh_attempt` answers the question from real use, for the 24 hours the rows live; the fetch also logs `Wake sent.`, `The car came online after the wake.` and `The car did not come online after the wake.` with `state_before` and `seconds_after_wake`. A 408 on `wake_up` itself is `WakeFailed` (not counted, not offered again). Tests cover it (`WakeFetchTest`).
- `OdometerFetcher::wake()` checks the scope and the cap under the vehicle lock, then `Tesla\Service\TeslaVehicleWaker::wake()` sends `POST /api/1/vehicles/{vin}/wake_up` (`VehicleCommandClient`, impl. `Client\TeslaWakeClient`, plain HTTP client: a wake is billed and never retried; no signed command, no Vehicle Command Protocol, no virtual key). 401 and 403 become `WakeScopeMissing` (outcome `WakeScopeMissing`, the connection stays usable); 408 is `Offline` and not counted. On success the attempt is `Waking` with `woke_at`, and the same message is queued again with `wakeDeadline` (wake + 90 s) and a 10 s `DelayStamp`: no worker sleeps. Each poll asks `GET /api/1/vehicles` (the list, via `TeslaVehicleWaker::isOnline()`, much cheaper than a wake); online leads straight to the billed live read (the state is not asked again), 90 s without it ends `WakeTimeout` and keeps the last reading. Unverified: whether the polling calls are billed, the `wake_up` answer shape, whether an `offline` car can be woken.
- The cap is a rolling 24 hours from each `wake_up` sent (`WakeWindow`, `WakeCap`), per vehicle, from `TeslaApp::$dailyWakeCap` (default 3, 0 turns waking off, set on `/settings/tesla`). Wakes are counted from `RefreshAttempt::$wokeAt` rather than a `RateLimiter`: the limit is per user and changes, the window is exact, the check and the send happen under the vehicle lock, and tests freeze the clock. A wake does not bypass the hourly manual refresh limit: the read that follows spends it.
- While an attempt is `Waking` (until the deadline plus 30 s, `WakeWindow::pendingSince()`), any other fetch of the vehicle backs off: a scheduled one is queued again 30 s later with the same `attempt`, a manual one ends `Busy`. The lock itself is held one step at a time.
- `vehicle_cmds` is requested with the other scopes (`TeslaScopes::REQUESTED`), never `vehicle_location`. A stored connection without it (`OAuthToken::canWake()`) is not offered the wake; the component shows "Reconnect to allow waking", a link to `tesla_reauthorize` (`/settings/tesla/connect/reauthorize`) which goes through `/authorize` with `prompt_missing_scopes=true`.
- "Asleep or offline" is `RefreshOutcome::isWakeable()` and `NoReadingReason::isWakeable()`; ask them rather than listing the cases.

### Lease and Reading: readings and the projection

- The projection is measured from the latest instant the car is known to be at an odometer, not from the clock. A value read from the car that equals the latest reading is not stored again: `OdometerReadingService::recordFromApi()` notes it as `OdometerReading::verify()` (`last_verified_at`, forward only, never past the clock, only on the latest reading). `LeaseTermsService::samples()` adds a sample with the same odometer at `last_verified_at`, so a day without driving moves the allowance to date and grows the margin; a verification a later reading contradicts is dropped. A car that cannot be read (asleep, offline) confirms nothing, so the figures stay as of the last answer.
- A refused reading is `ReadingRejected`; `Reading\Service\ReadingRejectionMessage` writes its message with the time of the neighbouring reading in the owner's time zone (the page and the console use it).

### Lease: returned lease (#49)

- `LeaseContract::$returnedAt` (nullable UTC instant) says the car went back to the bank. The user gives a calendar date in the lease settings (`/vehicles/{id}/lease`, card below the terms form, POST `lease_return` and `lease_return_undo`, kit Dialog to confirm, CSRF on both); `LeaseReturnService::markReturned()` (with `undoReturn()`, `isReturned()`, `returnedAt()`, `returnedOn()`; `LeaseTermsService` keeps the terms and the assessment) stores the START of the next day in the owner's time zone, so readings of the return day count. The date cannot be before the lease start nor after today (owner's zone); `updateTerms()` keeps `returnedAt`, and a new start on or after it is `LeaseTermsRejected::START_AFTER_RETURN`. Undo clears it. In UI text "return" (FR "restitution", "rendue") means the car handed back only; the lease-end convention says "the day after the last day".
- `LeaseStatus::Returned` / `DashboardState::Returned`: `LeaseAssessor::assess()` takes the instant (never the entity), counts the samples up to and including that instant and leaves out the later ones, never reads the clock for the status, and gives final figures: driven at the last sample up to the return, `projectedAtEnd` = driven (no forecast), excess = driven beyond the WHOLE allowance (no proration, also for an early return), no budget, no weekly cut. `LeaseTermsService::samples()` (and `readingSamples()`, the readings alone, for the chart) drops readings after the return and cuts a verification that runs past it at the return. Readings after the return stay stored, so an undo brings them back.
- Manual entry keeps working after the return: the reading is stored and the controller adds a `warning` flash saying it is not counted (`flash.reading_added_after_return`).
- Events `Lease\Event\LeaseReturned` and `LeaseReturnUndone`; see "Risk level changes" and "Scheduled fetching" for what listens. Fetching asks `LeaseReturnService::isReturned()` only.

### Lease: projection snapshots (#48, #107)

- `Lease\Entity\ProjectionSnapshot` (table `projection_snapshot`) keeps what Polaris projected for a lease at the owner's midnight: `localDay` (the date the midnight OPENS, midnight UTC as a label: the row of 7 November is taken at the very start of the 7th and describes the end of the 6th, so "today's snapshot" is the row with today's date), `cutoffAt` (the midnight instant, UTC; the zone may change later), `computedAt` (the clock of the run), `asOf` (the latest reading at or before the midnight, which can be days older), driven, allowed to date, projected end, daily budget (integer metres), risk level, and the pace the projection used: `overallPaceMetresPerDay`, `recentPaceMetresPerDay` (null before 30 days of lease) and `blendedPaceMetresPerDay` as floats (m/day; the driver binds a float with 14 significant digits, so a stored pace equals `Projection::blendedPace` to within 1e-9 m/day, compare with a delta); getters return `Lease\Domain\Pace`. Unique `uniq_projection_snapshot_lease_day` on (lease contract, `local_day`); the FK to `lease_contract` is `ON DELETE CASCADE` (derived data, like `VehicleDataSnapshot`). Rows saved before #107 (UTC day label, taken at 23:50 UTC) have no `cutoffAt` and no pace (null) and are kept; a new row with the same label replaces one.
- `Lease\Service\ProjectionSnapshotService::save(Vehicle, OwnerMidnight)` is the only writer (the message handler and `polaris:lease:snapshot [--vin=]`, which takes the owner's latest midnight, only call it). It uses `LeaseTermsService::assessAt($vehicle, $midnight->at)`: only readings and verifications recorded up to that midnight count (a verification of a later instant is left out, not cut there: it was not known then), `LeaseAssessor` judges the lease at that midnight (ended or not, time left), so the figures are the same whenever the job runs. A car returned at or before the midnight is `Returned` (not saved); a return after it is ignored (the car was leased then). Under a `symfony/lock` lock `lease_snapshot_<contract base32>` (non-blocking, TTL 60 s: `SnapshotOutcome::Busy`, retried once 30 s later by the handler). The last run for the same midnight wins (`Updated`); a `UniqueConstraintViolationException` on insert ends `Concurrent` (the entity manager is closed after it). `Lease\Domain\SnapshotPolicy` says which statuses are kept.
- Saved for `Active` and `Ended` leases. Not saved: no contract, `NoData`, `Returned` (final figures, the dashboard shows them; snapshots already stored stay), and an assessment that throws `LeaseTermsRejected` (`SkippedNotAssessable`).
- Trigger: `OwnerMidnightPassed` (see "Owner's midnight"). No catch-up beyond the latest missed midnight; a late run records the projection at the midnight with `computedAt` of the run.
- Rows are recomputed on a change of the terms a projection depends on, and on nothing else; an undone return or a past-dated reading never touches one. Lease start, end date (with its convention), allowance and start odometer count; tolerance, excess cost and currency do not (the panels use no risk level or money, and a stored risk level is refreshed by the next recalculation anyway). `LeaseContract::updateTerms()` returns whether one of them changed and moves `LeaseContract::$termsRevision` in the same flush, so `LeaseTermsSaved::$projectionChanged` is true only for a real change of an existing contract (a new contract has no snapshot, and the form fires the event on every save). `Lease\EventListener\QueueProjectionRecalculation` turns it into one `RecalculateProjectionSnapshots` (reports for the vehicle) on `async`; the request does not wait.
- `ProjectionSnapshotService::recalculate()` (handler `RecalculateProjectionSnapshotsHandler`; still the only writer with `save()`) holds the same `lease_snapshot_<contract>` lock as the midnight job for the whole run (refreshed per row), refreshes the contract once locked, and assesses each row again with `LeaseTermsService::assessAt()` at its stored `cutoffAt`. So a midnight job is either finished before (its row is rewritten) or starts after (it reads the new terms): no row stays under the old ones. Whichever finds the lock taken answers busy: the job is queued once more 30 s later, the recalculation throws `RecoverableMessageHandlingException` (Messenger retries it, then `failed`). A row becomes `Ended` when its midnight is now past the end. A row is deleted when it cannot be assessed: no `cutoffAt` (saved before #107), a midnight before the lease start, no data, readings that do not fit the terms, a draft, or a midnight at or after a return. An identical result leaves the row alone (`hasSameFigures()`); a changed one gets the clock of the run as `computedAt`. The handler logs one line per lease with `recomputed`, `deleted` and `unchanged`.
- Staleness: `LeaseContract::$snapshotsRevision` is the `termsRevision` the rows follow; `hasStaleSnapshots()` is `snapshotsRevision < termsRevision`. The run moves it forward to the revision it read, never backwards, so an edit made meanwhile stays stale until its own queued recalculation has run.
- What else a recalculation picks up besides the terms (accepted: a row is now "what Polaris would have projected at that midnight with the current terms and the readings stored now"): readings entered later with a past date, the current `polaris.lease.recent_pace_weight`, and verifications, with `assessAt()`'s own rule (a verification recorded after the midnight is left out, but only the latest one per reading is kept in `lastVerifiedAt`, so an older verification that a later one replaced is gone).
- `Lease\Service\ProjectionHistoryService::history(Vehicle, ?from, ?to)` returns `list<ProjectionSnapshotPoint>` (readonly DTO: `localDay`, `cutoffAt`, `computedAt`, `asOf`, `Distance` figures, `RiskLevel`, `?Pace` overall, recent and blended), oldest local day first, bounds inclusive and read as calendar dates. The effective odometer of a projected-versus-actual chart comes from the readings, not from the snapshots; the chart is not built yet and `Dashboard` must map these into its own types.

### Lease and Dashboard: actual versus predicted panels (#107)

- Three panels on the dashboard of an Active lease only (hidden for no lease, no reading, draft, ended, returned), each a kit Card with a 4-row Table of two columns (the header row has no hover colour) (`Dashboard:ComparisonPanel`, anonymous; `data-comparison`, `data-period`, `data-figure`, `data-no-history` are what tests read; while no period has history the panel shows one line instead of the table). Rows: today, last 7, 14 and 30 days. A positive difference means more than expected. Each row has the period with the two figures under it (small, muted) and the gap on the right (larger, with its percentage under it, signed); figures come from the `km` and `percent` filters (see UI), only the digits are monospaced.
- Every window ends at the latest reading (`Projection::asOf`), never at the clock. "Today" starts at the owner's last midnight at or before it (`OwnerMidnight::latestAt()`); the 7, 14 and 30 day windows start at the owner's midnight that many days before, and use the snapshot of that local day, matched exactly, never the nearest. No snapshot for the day, or a start before the lease start: "not enough history" (row without figures). One exception, "today" only: without a stored snapshot of its own day (the midnight job has not run yet, or was missed), `ActualVersusPredictedService` rebuilds its figures in memory with `LeaseTermsService::assessAt()` at the owner's midnight (the job's own computation, never saved, so a stored row stays the record of what was projected then); only when that gives nothing (no data before the midnight, lease not running then) does it use the latest earlier snapshot and is measured from that snapshot's midnight; the row then says "Since yesterday" / "Since N days ago" (`WindowComparison::$fallbackDays`, `ComparisonRow::$fallbackDays`, key `compare.period.since_days`), and the 7, 14 and 30 day rows never fall back. After deploy the 7, 14 and 30 day rows fill in over a week, two weeks and a month. While the snapshots are stale after a terms edit (see "Projection snapshots"), `ActualVersusPredictedService` reads none of them: only "today" shows, rebuilt in memory under the current terms, the other rows are empty and say "Recalculating" (`PredictionComparison::$recalculating`, `ComparisonPanels::$recalculating`, `data-recalculating`), and a line asks to reload the page; the figures come back when the recalculation has run.
- Driving hours: `LeaseContract::$quietFrom` / `$quietUntil` (local `HH:MM`, both or none; card on `/vehicles/{id}/lease`, POST `lease_driving_hours`, `DrivingHoursService` the only writer) say when the owner usually does not drive. `Lease\Domain\QuietHours` (owner's zone, rebuilt per local day so DST nights have their real length) makes `OdometerTimeline::odometerAt()` interpolate on active time instead of clock time: between two readings the odometer stays still in the quiet hours, so a 21:00 reading no longer gives the night to the day before. Two readings inside one quiet period fall back to linear for that pair. Only `LeaseTermsService::odometerTimeline()` passes them, so the window starts of the panels use them; `ProjectionCalculator` and the snapshots do not (no recalculation, `termsRevision` untouched). Nothing set keeps the linear behaviour.
- Panels: (1) budget: distance driven in the window against the snapshot's daily budget times the window length; (2) pace: against the snapshot's blended pace times the window length (a row saved before #107 has no pace: no result); (3) projected end: the projected distance at the lease end now against the snapshot's, no odometer needed. The percentage is the difference over the expected distance; expected 0 shows the km only.
- `Lease\Domain\PredictionComparer` (plain PHP, takes the timeline, the latest projection, the zone and the snapshots as `SnapshotFigures` by local day) does the work; `Lease\Service\ActualVersusPredictedService::compare()` gathers them (`LeaseTermsService::assess()` and `odometerTimeline()`, `ProjectionHistoryService`). `Lease\Domain\OdometerTimeline` is the odometer over time (linear between samples) shared with `ProjectionCalculator`. `Dashboard\Service\ComparisonPanelsMapper` maps the result into the dashboard's own DTOs (`ComparisonPanels`, `ComparisonRow`, `ComparisonFigures`).

### Alert: risk level changes (#29)

- The self-hosted app sends no alert: it detects that a vehicle's risk level got worse and tells `Extension\RiskAlertNotifier`, which the hosted layer replaces (service decoration or alias). The default `NullRiskAlertNotifier` does nothing and returns null.
- Triggers are events from the modules that move the projection, never calls into Alert: `Reading\Event\ReadingStored` (manual or API reading stored), `Reading\Event\ReadingVerified` (the car had not moved), `Lease\Event\LeaseTermsSaved`. `Lease\Event\LeaseReturnUndone` queues a check too (the lease is assessed again); `LeaseReturned` queues none, as a returned lease is not assessed. `Alert\EventListener\QueueRiskLevelCheck` turns each into a `CheckRiskLevel` message on the `async` transport, so the check never delays a reading or a fetch. A new writer of readings or terms must dispatch the matching event.
- `Alert\Service\RiskLevelWatcher::check()` runs under a `symfony/lock` lock per vehicle (`risk_alert_<vehicle base32>`, non-blocking, TTL 60 s): a scheduled fetch and a manual reading landing together are serialised, and the second check reads the row of the first. A busy check ends `RiskCheckOutcome::Busy`; `CheckRiskLevelHandler` queues it once more 30 s later.
- The known level is the newest `AlertLog` row of the vehicle (table `alert_log`: `sent_at`, `type`, `risk_level`, nullable `channel`). A row is written whatever the extension does; `channel` is what `notify()` returned, null when nothing was sent. `Alert\Domain\RiskChangeRule` decides from ranks (Ok 0, Watch 1, Over 2; a Domain does not use another module's Domain): same level does nothing; a first assessment or a lower level is logged as `baseline` without a call; a higher level calls `notify()` with a `RiskLevelChange` (vehicle, previous, current, `LeaseAssessment`) and is logged as `risk_increased`. If `notify()` throws, no row is written and the message is retried by Messenger.
- No contract, no readings, and a lease that is a draft, has ended or is returned are not assessed and write nothing.

### Extension: optional hosted bundle

- `config/bundles.php` registers `Polaris\Hosted\HostedBundle` (`['all' => true]`) only when `class_exists()` finds it; this repository ships no such class, so a self-hosted install loads nothing more (`OptionalBundleTest`). The name is generic on purpose: it says nothing about what the hosted layer does. The class sits in `src/Hosted/`, which the `Polaris\` PSR-4 root already maps, so the hosted image adds the file and no Composer change.
- The prod image keeps no Composer in its final stage (`debian:13-slim`) and dumps a classmap-authoritative autoloader (an unlisted class is not found) with a cache warmed at build time. A downstream image therefore adds its `src/Hosted/` in a builder stage (`FROM` a Composer-capable image, copying `/app`), runs `composer dump-autoload --classmap-authoritative --no-dev`, clears and warms `var/cache` with `APP_ENV=prod`, and copies the result. Not run end to end here: unverified until the hosted image is built.

### Shared and Account: error reporting

- Optional Sentry reporting, off by default. `POLARIS_ERROR_REPORTING` (`off`, `maintainer`, `custom`) is turned into the DSN by `Shared\Reporting\ErrorReportingDsnProcessor` (`%env(polaris_dsn:...)%` in `config/packages/sentry.yaml`); `maintainer` reads `polaris.sentry.maintainer_dsn` (empty until the maintainer fills it), `custom` reads `SENTRY_DSN`. No DSN means the SDK sends nothing. The Sentry bundle is registered for `prod` only (contrib recipes are off, so it was wired by hand from the recipe); tests boot `Polaris\Tests\Support\ProdKernel` (`SentryWiringTest`) and unit-test the rest.
- One scrubber, `Shared\Reporting\Scrubber`, behind `EventFilter` (`before_send`, `before_send_transaction`), `LogFilter` and `BreadcrumbFilter`. It removes VINs, tokens, secrets, keys, emails, location keys, and `vehicle_data` unless the user allowed details; odometer values and lease figures stay (decision of the maintainer). A new log context or span carrying a secret must be covered by a scrubber test.
- Whose data a report holds: `Shared\Reporting\ReportingContext` is set by `Account\EventListener\BindReportingUser` (web, on `kernel.controller`) and `Vehicle\EventListener\BindReportingUserOfMessage` (worker, for messages implementing `ReportsForVehicle`; a new message about a vehicle implements it, or `ReportsForUser` for one about an owner). `ReportingGate` reads the user's choice from the database at send time: opted out, unknown user or unreadable choice drops the report (fail closed); no user follows the instance switch. `sentry.messenger.isolate_context_by_message` is on. Only the user ULID is attached.
- Worker heartbeat: `Shared\Reporting\WorkerHeartbeat` (prod only) sends a Sentry Crons check-in (`ok` or `error`, with the duration) for the `DispatchDueFetches` message that comes out of the scheduler (it carries a `ScheduledStamp`), one monitor per instance (`DispatchOwnerMidnights` has none: same worker, and Sentry bills each monitor, the free plan includes one), schedule every minute, margin 2 minutes, three failures open an issue. It sends for `custom` only (every instance is a monitor and Sentry bills each one, so the maintainer's project does not take them), nothing for `maintainer`, `off` or without a DSN. A tick has no user, so the user opt-out cannot apply, and check-ins do not pass through `before_send`: they carry only a slug, a status and a duration. The slug holds an instance id (`hash_hmac` of `kernel.secret`) so instances sharing one Sentry project do not mix. Unverified against a real Sentry project: that the monitor is created by the first check-in.
- Per user: `User::$errorReporting` and `$errorReportingDetails` (details need reports), set in Settings through `UserSettings::changeErrorReporting()`. New users get `Extension\ErrorReportingPolicy::defaultForNewUser()` (self-hosted: true; the hosted layer replaces it with false until the user agrees).
- `data_collection` in `sentry.yaml` writes every key explicitly (all off); `trace_propagation_targets` is `[]`; `zend.exception_ignore_args = On` in the prod ini. Monolog is installed: prod logs go to stderr from `info` (no fingers_crossed), warnings and above also go to Sentry logs.

## Delivery

### Secrets

- Never commit a secret, not even a dev `APP_SECRET` (GitGuardian scans every PR). Generated values go in `.env.local`.
- `.env.example` lists every per-install variable (secret, password, API key) with an empty value; add new ones in the same PR.

### Git

- Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`); PR titles are checked in CI.
- Versions and `CHANGELOG.md` come from release-it: don't edit by hand.
- `main` is the released code (tags, image `latest`); `dev` is the next release and its tip is built every night into the image `nightly-<commit>`, and `latest-nightly` moves to it (`nightly.yml`). Branch from `dev` and open PRs against it, except a fix that cannot wait, which goes to `main` and is merged back into `dev`.
- One issue per small PR, with "Closes #N"; squash-merged into `dev`. A release is a PR `dev` to `main` merged with a merge commit (never squashed), then the Release workflow.
- No `.bak` or backup copies: git is the history.

### Definition of done

- Tests pass (unit for `Domain/`, functional for controllers and commands), PHPStan, php-cs-fixer and Deptrac pass (`make ci` runs all four), docs updated (`docs/self-hosting.md` with any change to the compose files, the environment variables or the Tesla setup), story acceptance criteria met.
